# Design

## Context

См. proposal.md и specs/input-boolean-export/spec.md. `RelayEntity` уже вызывает сервисы по домену entity_id; YAML override создаёт этот адаптер для input_boolean без новой модели данных. Мастер использует CATEGORY_DOMAIN_MAP.matches, а автоматическая фабрика берёт первую категорию по preferred_rank. Сейчас relay имеет rank 10, scenario_button — 12, поэтому простое расширение domains поменяет автоматический выбор.

Командный dispatcher публикует оптимистический echo после попытки сервиса, в том числе при ошибке. Этот механизм нужен физическим устройствам (issue #35), но несовместим с новым контрактом input_boolean. Редактирование категории уже использует hot-apply и ConfigPublishGate; локальные redefinitions можно сохранить без новых механизмов.

## Goals / Non-Goals

**Goals:** переиспользовать существующие адаптеры и настройки; сохранить автоматический выбор; подтвердить новый режим реальным состоянием; объяснить направление обмена пользователю.

**Non-Goals:** универсальные виртуальные устройства, новые домены, изменение глобального поведения echo и автоматическая миграция облачных сценариев.

## Decisions

1. Добавить input_boolean в domains relay и поставить scenario_button перед relay в preferred_rank. Другие домены не конкурируют с scenario_button, поэтому их выбор не меняется. Альтернатива — новый per-domain rank/флаг автоматического выбора — добавляет ненужную модель конфигурации ради одной пары категорий.
2. Использовать существующий override UI/YAML; приоритет UI → YAML → auto сохраняется. Мастер уже поддерживает сущности без device_id. Новых настроек режима нет.
3. Для relay из input_boolean оптимистическое echo не накладывает командные значения на состояние. `RelayEntity.sanitize_echo_states` использует фактический baseline для этого сочетания домена и категории; остальные адаптеры сохраняют поведение. Проверяются ошибка сервиса и смешанная команда с физическим relay.
4. Подсказки в мастере и строке устройства объясняют обе семантики. Смена категории показывает предупреждение о связях сценариев. Использовать существующие Lit-компоненты и локализацию ru/en/EN_FALLBACK, без нативных confirm/alert.
5. Выполнять связанные шаги последовательно в ветке feat/input-boolean-relay. В конце — независимое ревью всей реализации. Внешние публикации и релиз в эту задачу не входят.
6. Удаление HA-состояния (`new_state=None`) для input_boolean в relay передаётся через существующий обработчик primary state как unavailable. Это закрывает требование отсутствующей сущности без изменения прежнего поведения удаления в других доменах или legacy. Проверяется удаление и восстановление на настоящем HA, включая MQTT-публикацию; refresh и delayed-confirm сохраняют выставленный offline.

## Risks / Trade-offs

- Ошибка rank мигрирует старые сущности → отдельные тесты defaults и неизменных доменов.
- Оптимистический echo выдаёт фиктивный успех → тесты dispatcher/publisher с задержанным состоянием и ошибкой сервиса.
- Изменение категории сбрасывает облачные привязки → предупреждение до изменения; локальные имя/комната и остальные устройства сохраняются.
- Новый интерфейс скрывает legacy-направление → подсказки явно сообщают on→click, off→double_click.

## Migration Plan

Установка обновления не меняет categories или options. Пользователь выбирает relay явно. Возврат к auto восстанавливает прежний событийный выбор; HA-состояние от смены представления не переключается. Категория в облаке может перерегистрироваться в обе стороны, о чём предупреждает UI.
